# TASK_CARD — T-20261112-1 due-dates-overdue (круг r1)

## Суть

У задачи появляется необязательный срок `dueDate` — календарная дата `YYYY-MM-DD` без времени: его можно
задать при создании, поменять и убрать. Сервер сам отбрасывает неверный формат и несуществующие дни
(400, тот же формат ошибок `{ errors: [...] }`). В списке срок виден рядом с названием, просроченные
открытые задачи выделены красным, над списком — переключатель «Все / Просроченные». «Просрочена» =
срок строго раньше сегодняшнего дня по локальным часам пользователя; выполненные задачи просроченными
не бывают; счётчик «N open» не меняется.

Часть комментариев коллеги в работу не идёт (см. реестр, R-20, R-23 … R-26, R-28): вложенный тест ничего не проверяет,
коммит `.env` и `git push --force` запрещены правилами проекта.

## Критерии приёмки

Сервер проверяется тестами supertest в `server/test/` (`bash scripts/node.sh npx vitest run server/test/tasks.test.ts`)
и/или `curl` на `http://localhost:3001`; UI — тестами Testing Library в `web/src/` и глазами на `http://localhost:5173`.

**Контракт и сервер**

- **AC-1** (A1): задача создаётся без срока, как раньше. Проверка: `POST /api/tasks {"title":"A"}` → 201; в ответе
  и в `GET /api/tasks` у задачи нет значения срока (`dueDate` отсутствует или `null` — одно представление на весь
  контракт, фиксирует планировщик). Существующие 11 серверных тестов остаются зелёными либо меняются только в
  части ожидаемой формы задачи.
- **AC-2** (A2): срок задаётся при создании. Проверка: `POST /api/tasks {"title":"A","dueDate":"2026-12-01"}` → 201,
  в ответе `dueDate === "2026-12-01"`; следующий `GET /api/tasks` возвращает ту же строку. (Ловушка:
  `server/src/store.ts:20-25` собирает задачу по полям вручную — срок теряется, если его туда не добавить.)
- **AC-3** (A3): срок хранится и отдаётся строкой `YYYY-MM-DD` без времени и пояса. Проверка: значение в ответе
  соответствует `/^\d{4}-\d{2}-\d{2}$/` и побайтно равно отправленному (сервер не превращает его в ISO-таймстамп).
- **AC-4** (A2): срок меняется. Проверка: `PATCH /api/tasks/1 {"dueDate":"2027-01-15"}` → 200, `dueDate === "2027-01-15"`,
  `title` и `done` не изменились; PATCH только с `dueDate` НЕ отвечает `nothing to update` (`server/src/validate.ts:38`).
- **AC-5** (A2, A1): срок убирается. Проверка: `PATCH /api/tasks/1 {"dueDate":null}` → 200; в ответе и в `GET` срока
  нет (то же представление, что в AC-1). PATCH других полей (`{"done":true}`) срок НЕ сбрасывает.
- **AC-6** (A1): неверный формат отклоняется на POST. Проверка: каждое из `"12.11.2026"`, `"2026-1-5"`,
  `"2026/11/12"`, `"2026-11-12T10:00:00.000Z"`, `"завтра"`, `""`, `20261112` (число), `true`, `{}` в поле `dueDate`
  → 400, задача не создана (`GET` не изменился).
- **AC-7** (A1, A3): несуществующие дни отклоняются. Проверка: `"2026-02-30"`, `"2026-02-29"` (не високосный),
  `"2026-04-31"`, `"2026-13-01"`, `"2026-00-10"`, `"2026-11-00"` → 400; `"2028-02-29"` (високосный) → 201.
- **AC-8** (A5): ошибка «как у остальных полей». Проверка: тело ответа — `{ "errors": [ … ] }` (как
  `server/src/app.ts:22`), в массиве есть строка, называющая поле `dueDate` и ожидаемый формат; при одновременно
  плохих `title` и `dueDate` в `errors` присутствуют обе ошибки (валидация накапливает, как `validate.ts:24-26`).
- **AC-9** (A2): те же правила на PATCH. Проверка: `PATCH /api/tasks/1 {"dueDate":"2026-02-30"}` и
  `{"dueDate":"12.11.2026"}` → 400, срок задачи в `GET` остался прежним.

**UI — отображение и фильтр**

- **AC-13** (A1): срок показан рядом с названием. Проверка: у задачи с `dueDate: "2026-12-01"` в её же `<li>` виден
  текст срока (формат — см. вопрос 2, по умолчанию `2026-12-01`); у задачи без срока ни даты, ни заглушки нет.
- **AC-14** (A4, A3): просроченная выделена красным. Проверка: при «сегодня» = 2026-11-12 строка открытой задачи
  со сроком `2026-11-11` имеет отдельный CSS-класс просрочки и красный цвет (computed `color` красный; в проекте
  красный уже есть — `web/src/styles.css:8`, `#c62828`); строки со сроком `2026-11-12`, `2026-11-13` и без срока
  этого класса не имеют.
- **AC-15**: над списком есть переключатель с двумя вариантами «Все» и «Просроченные», по умолчанию активен «Все».

  видны все задачи.
- **AC-16** (A4): режим «Просроченные» показывает только просроченные. Проверка: список из четырёх задач — срок
  вчера, срок сегодня, срок завтра, без срока (все открыты) → после переключения видна только первая; возврат на
  «Все» показывает все четыре.
- **AC-17** (A1): пустой результат режима. Проверка: в режиме «Просроченные» при отсутствии просроченных (включая
  полностью пустой список задач) показан ровно текст «Нет просроченных задач», а текст «No tasks yet.» в этом
  режиме не показан; в режиме «Все» при пустом списке по-прежнему «No tasks yet.» (`App.tsx:31-32`).

**Правило просрочки**

- **AC-18** (A3): граница «сегодня». Проверка (юнит-тест настоящей `isOverdue`, `now` передаётся аргументом и
  создаётся локальным конструктором, например `new Date(2026, 10, 12, 15, 0)`): срок `2026-11-11` → `true`;
  `2026-11-12` → `false`; `2026-11-13` → `false`; без срока → `false`. Утверждения — `toBe(true)` / `toBe(false)`.
- **AC-19** (A3, главная ось): «сегодня» — локальный день пользователя, не UTC. Проверка: тесты из AC-18 плюс два
  граничных прогоняются в двух поясах — `TZ=Europe/Chisinau bash scripts/node.sh npx vitest run web/src/overdue.test.ts`
  и `TZ=America/New_York …` — и зелёные в обоих:
  (а) локальное время 12.11.2026 00:30 (в UTC+2 это ещё 11.11 по UTC): срок `2026-11-11` → просрочена,
  срок `2026-11-12` → нет;
  (б) локальное время 11.11.2026 23:30 (в UTC−5 это уже 12.11 по UTC): срок `2026-11-11` → НЕ просрочена,
  срок `2026-11-10` → просрочена.
  Реализация через `toISOString().slice(0, 10)` или `new Date("YYYY-MM-DD")` должна на этих кейсах падать хотя бы
  в одном из поясов (это и есть контроль, что тест различает).
- **AC-20** (A4): выполненные не просрочены. Проверка: задача `done: true` со сроком `2020-01-01` —
  `isOverdue` → `false`; в UI строка без красного класса; в режиме «Просроченные» её нет. Отметить просроченную
  задачу выполненной в режиме «Просроченные» → строка исчезает из списка; снять отметку (в режиме «Все») → строка
  снова красная.
- **AC-21** (A4): счётчик не тронут. Проверка: заголовок — `Tasks (N open)`, где N = число невыполненных задач
  всего списка (`App.tsx:16,20`); N одинаков в режимах «Все» и «Просроченные» и не зависит от сроков. Существующие
  проверки заголовка в `web/src/App.test.tsx:46,54` остаются зелёными без правки ожиданий.

- **COMPLEXITY: medium** — две области (сервер и UI) и изменение контракта между ними. По точкам входа выше:
  правка ~7 существующих файлов (`types.ts`, `validate.ts`, `store.ts`, `api.ts`, `useTasks.ts`, `App.tsx`,
  `styles.css`) + 2 новых (`overdue.ts`, `overdue.test.ts`) + дополнение двух файлов тестов. Не `high`: нет

  задетый пункт = high. Дополнительные факторы: поведение зависит сразу от нескольких осей (A3 дата/пояс,
  A4 состояние, A2 POST/PATCH, A1 границы); на новую логику тестов нет, а предложенный готовый тест — ложный PASS
  (R-20). Смягчает: откат — revert коммитов без потери данных; на существующий код тесты есть (15 зелёных).
- Следствия по `pipeline.*`: план проверки до кода обязателен (`qa_plan_risk: [high]`), приёмка на живой сборке,
  ревью плана тестов и `/kit-mr-self-review` — тоже.

## Вопросы

Все три — продуктовый выбор; работа может идти с вариантами по умолчанию.

1. **Язык новых надписей.** Интерфейс сейчас английский («Tasks (N open)», «New task», «Add», «No tasks yet.» —
   `App.tsx:20-32`), а ТЗ даёт русские тексты «Все / Просроченные» и «Нет просроченных задач». Оставить новые
   надписи по-русски дословно, как в ТЗ, или перевести под остальной интерфейс?
   **По умолчанию:** дословно по ТЗ, по-русски (критерии AC-15, AC-17 написаны так); существующие английские
   надписи не трогаем.
2. **Как показывать срок и что именно красить.** ТЗ говорит «показываем срок» и «выделяем красным» без формата и
   без указания, что красное — дата, название или вся строка.
   **По умолчанию:** срок показываем как есть, `2026-12-01`; у просроченной красным (`#c62828`) — и название, и
   дата.
3. **Срок в прошлом.** Можно ли поставить срок раньше сегодняшнего дня (при создании или изменении)?
   **По умолчанию:** можно — сервер проверяет только формат и существование дня (он не знает «сегодня»
   пользователя), задача сразу отображается как просроченная.
