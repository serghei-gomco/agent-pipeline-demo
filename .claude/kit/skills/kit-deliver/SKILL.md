# /kit-deliver — сдача

Два гейта, каждый — одно «да» человека в том же сообщении. Всё необратимое сверх них — отдельное «да».
Правила git — `docs/CONVENTIONS.md` п. 9.

## Шаг 0 — машинный гейт

1. `.agent-kit.yml` есть; папка задачи найдена (`python3 .claude/kit/scripts/state.py <KEY>`).
2. `python3 .claude/kit/scripts/check_gates.py --stage deliver <task_dir>`. Любой ✗ — СТОП, показать
   вывод. Гейт сверяет: вердикт ревью, `GATES_AFTER_QA: ok`, `ACCEPTANCE: PASS` при required,
   `MR_SELF_REVIEW: APPROVED`, если он требовался.
3. Нужен ли `/kit-mr-self-review`: если риск плана входит в `pipeline.test_plan_review_risk`, дифф
   задевает `danger` или это круг возврата — и `MR_REVIEW.md` нет — сначала он.

## Шаг 1 — подготовка показа (без «да», только чтение)

- Ветка: не базовая, не из `git.protected_branches`, совпадает с `git.branch_pattern`.
- Upstream: нет или `<remote>/<своя ветка>`; указывает на базовую — СТОП.
- `git status`: незакоммиченного по задаче нет (при `commit_mode: off` — закоммитить сейчас,
  коммит не требует «да»: явные пути, сообщение по `git.commit_pattern`).
- `git fetch <remote> <base_branch>`; отставание от базы и конфликты (`git merge-tree` или пробный
  дифф). Конфликт — СТОП: нужен rebase или merge базы — это отдельное «да», не часть гейта.
- Дифф: `git diff --stat $(git merge-base HEAD <remote>/<base_branch>)` и сам дифф.
- Черновик описания PR (ниже).

Показать человеку: ветка, коммиты (`git log --oneline <merge-base>..HEAD`), stat, итоги ревью/QA/
приёмки одной строкой каждый, черновик описания. Вопрос: «Код: пуш + PR? (да/нет)».

## Шаг 2 — гейт кода (по «да»)

1. Ещё раз ревью диффа глазами (то же, что показано; изменилось — показать заново).
2. `git push -u <remote> <ветка>`. Никогда `--force`; `--force-with-lease` — только отдельным «да».
3. Проверить: `git rev-parse --abbrev-ref @{u}` = `<remote>/<ветка>`.
4. PR/MR по `git.host`:
   - `github` → `gh pr create --base <base_branch> --head <ветка> --title … --body-file <файл>`;
   - `gitlab` → `glab mr create --target-branch <base_branch> --source-branch <ветка> --title … --description …`;
   - `none` → отдать заголовок и описание текстом для ручного создания.
5. Показать результат: ссылку/номер PR. Между шагами 2–4 не переспрашивать; любая ошибка — СТОП.

### Описание PR

```
## Что          — 2–4 строки
## Зачем        — ключ задачи и ссылка (если трекер есть), суть ТЗ
## Как проверено — прогоны (тесты/линт/типы) с итогами, приёмка (вердикт, число кейсов)
## Не проверено — из QA_REPORT/ACCEPTANCE, дословно
## Заметки      — NOTE-строки (мелочи, найденные по ходу), DEFER-находки ревью со ссылкой
```
Без AI-атрибуции, если `git.forbid_ai_trailers: true`.

## Шаг 3 — гейт трекера (`tracker.kind` ≠ `none`)

Показать: текст комментария (итог QA для человека: что сделано, как проверить — из «Инструкции для
тестировщика», что не проверено, ссылка на PR) и целевой статус. Вопрос: «Трекер: комментарий +
статус? (да/нет)». По «да» — строго сначала комментарий, потом статус. `tracker.kind: none` —
шаг пропускается одной строкой. `tracker.kind: file` — дописать в файл трекера проекта.

## Мёрж — только по явной просьбе человека

«Сливай» — разовая просьба, не шаг сдачи. До мёржа вслух: PR твой, цель — `base_branch`, конфликтов
нет, пайплайн/проверки зелёные, ревью и приёмка пройдены, открытых вопросов к владельцу нет. Нашлась
проблема — СТОП и показать. Мёрж в `git.protected_branches` иначе, чем через PR в `base_branch`, —
никогда. Удаление ветки после мёржа — отдельный пункт.

## Отдельное «да» всегда

rebase, merge базы в свою ветку, `--force-with-lease`, `reset --hard`, `cherry-pick`, `commit --amend`,
`branch -D`, переименование/перенумерация файлов миграций, любое действие с базовой веткой.
Порядок: проверка вслух (что теряется, где копия) → вопрос → «да» → команда.
