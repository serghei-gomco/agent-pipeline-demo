# /kit-mr-self-review — ревью PR до пуша

`kit-reviewer` смотрел рабочий дифф против плана. Этот шаг смотрит то, что увидит ревьюер PR:
итоговый дифф, описание и заявления о проверке — и ищет, где они не сходятся с кодом.
Рамка — `rules/adversarial-review.md`.

## Когда обязателен

Риск плана входит в `pipeline.test_plan_review_risk`, или дифф задевает пункт `danger`, или это круг
возврата. В остальных случаях — по просьбе человека.

## 1. Вход (собирает главная сессия)

- `git fetch <remote> <base_branch>`; дифф `git diff $(git merge-base HEAD <remote>/<base_branch>)..HEAD`
  (только коммиты: то, что уйдёт в PR). Незакоммиченное по задаче есть — сначала закоммитить.
- `TASK.md`, реестр R-n и AC из карточки/плана.
- Черновик описания PR (как в `/kit-deliver`) и `QA_REPORT.md` — с пометкой «утверждения автора на
  проверку, не факты».
- НЕ передавать: `REVIEW.md` и любые вердикты, `CHANGES.md`, `STATE.md`, объяснения «почему так».

## 2. Запуск

Независимый агент (`kit-reviewer` или general-purpose) в чистом контексте. Промт:
1. первым абзацем — дословно блок «Режим — опровержение…» из `rules/adversarial-review.md`;
2. вход из п. 1 (пути к файлам, дифф);
3. задача: «проверь, что описание PR и QA-отчёт правдивы относительно диффа; что каждый AC реализован
   и проверен; что дифф не ломает соседних потребителей и пункты `danger`»;
4. формат находки: file:line или кейс, сценарий поломки, что нарушено.

Повторный проход: тот же промт плюс список прошлых находок (только формулировки) — отметить
«закрыта / осталась».

## 3. Сверка находок — главная сессия

Каждую находку проверить по коду (не принимать и не отбрасывать на веру) и отнести к классу:
- **принято** → чинить (FIX-HERE), новый коммит, затем новый проход;
- **контракт непонят** → ревьюеру не хватило входа: дописать вход и перегнать, код не трогать;
- **компромисс** → дефект есть, починка дороже риска: строка в описании PR / «Не проверено» с ценой;
- **шум** → верно без контекста, которого у ревьюера не было: одна строка, какого.

## 4. Стоп

- Не больше `pipeline.max_review_passes` проходов. После последнего с существенными находками —
  СТОП и показать человеку.
- Два прохода подряд с существенными находками и ни одной «принято» — «театр сомнений»: стоп,
  показать человеку таблицу сверки.

## 5. MR_REVIEW.md

`<task_dir>/MR_REVIEW.md` (на круге N — `MR_REVIEW-rN.md`):
```
head: <sha>   база: <remote>/<base_branch> @ <sha merge-base>   проход: K
## Вход              — что передано ревьюеру (список файлов)
## Находки и сверка  | # | находка | file:line | класс | действие |
## Что проверено     — из ответа ревьюера
MR_SELF_REVIEW: APPROVED | NEEDS_CHANGES
```
`APPROVED` — нет находок класса «принято» без исправления и нет «контракт непонят» без перегона;
`head` совпадает с текущим HEAD. Новый коммит после APPROVED — вердикт устарел, нужен дельта-проход.

## Границы

Не пушит, не открывает PR, не пишет в трекер. Код правит только обычным циклом (implementer или
главная сессия по находке «принято»), коммитом без «да».
