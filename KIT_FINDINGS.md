# KIT_FINDINGS — что нашлось в agent-kit на настоящей задаче (12.11.2026)

Кит не правил — только список. Версия kit: `0.1.0` (копия в `.claude/kit/`). Формат: что видно → почему важно → предложение.

| # | Где | Что видно | Почему важно | Предложение |
|---|---|---|---|---|
| K-1 | `install.sh → detect_config` | `commands.typecheck` пустой, хотя в `package.json` есть скрипт `typecheck`: детектор смотрит только на `tsconfig.json` в корне, а здесь `tsconfig.base.json` + `server/`, `web/` | Агенты не проверят типы — тихий пропуск проверки | Брать `typecheck` из `package.json` scripts первым, `tsconfig*.json` — запасной вариант |
| K-2 | `install.sh` / окружение | Команды пишутся как `npm test`, а `node` по умолчанию на машине — 16 (Vite 5/Vitest 2 требуют ≥ 18) | Агент получит падение, не связанное с задачей | Учитывать `.nvmrc`/`engines`: предупреждать при несовпадении или писать команды через обёртку (здесь — `scripts/node.sh`) |
| K-3 | `install.sh --user` + `install.sh <проект>` | Хуки зарегистрированы дважды: глобально и в `.claude/settings.json` проекта → каждый PostToolUse-напоминание приходит 2 раза, сторож git работает 2 раза | Шум в контексте, двойное время хуков | При установке в проект проверять глобальную регистрацию (или наоборот: хуки проекта no-op, если уже стоят глобально) |
| K-4 | `install.sh`, финальная подсказка | «Дальше: закоммить .claude/kit … .agent-kit.yml» — но собственный `commit_check` (F1) не пускает коммит в `main` (защищённая) | Первое же действие по подсказке упирается в сторож | В подсказке: «закоммить в отдельной ветке (`chore/agent-kit`) и влить через PR» |
| K-5 | `hooks/state-reminder.py` | «прошёл шаг сдачи (`git push`)» после команды, где `git push --force` был только ТЕКСТОМ внутри heredoc (запись ТЗ в файл) | Ложное напоминание; в другом месте такой же разбор может дать ложный вывод | Использовать тот же разбор команды, что и `git_policy.py` (он heredoc понимает — сторож не сработал) |
| K-6 | `hooks/lib/git_policy.py` vs `rules/git-gates.md` | `git push --force-with-lease origin <своя ветка>` → allow без запроса, а правило: «Всегда отдельное «да»: … `--force-with-lease`» | Правило текстом и механика расходятся — ровно то, от чего kit защищает | `res.ask(...)` для `--force-with-lease` (тест `scripts/test-hooks.sh` сейчас фиксирует фактическое поведение: allow) |
| K-7 | `git_policy.py` | Отказ «`git add … && git commit` одной командой» срабатывает и на служебные скрипты вне репо проекта (песочница во `mktemp -d`, другой репо) — оценивается по cwd сессии | Мешает писать тесты/скрипты; обход — выносить в файл | Определять репо цели по `cd`/`-C` внутри команды; если цель — не проект kit, пропускать |
| K-8 | Агенты `kit-*` | После `install.sh` агенты и скиллы `kit-*` появились в сессии не сразу, а примерно через 10 минут (после интейка и планера); первые два шага шли как general-purpose + «прочитай `.claude/agents/<имя>.md` и выполняй» | `/kit-task` сразу после установки не может вызвать агентов по имени | В README kit: «после установки перезапусти сессию»; в `/kit-task` — запасной путь general-purpose + файл агента |
| K-9 | `kit-planner` + `check_gates.py --stage plan` | Планер по инструкции гоняет гейт плана и при `risk: high` всегда получает ✗ «нужен QA_PLAN.md» — его пишет следующий агент после одобрения | Красный гейт на шаге, где он не может быть зелёным, приучает игнорировать ✗ | Разделить: `--stage plan` (структура плана) и `--stage pre-impl` (плюс QA_PLAN) |
| K-10 | `check_gates.py` реестр | Распознаёт только ячейку статуса ровно `IN`/`OUT`; интейк писал «IN (с оговоркой)» — планеру пришлось переносить оговорки в другую колонку | Интейк и гейт расходятся в формате | Описать формат ячейки в CONVENTIONS п. 5 и в kit-intake, или парсить первое слово |
| K-11 | `skills/kit-task` п. 2 vs п. 4 | П. 2: «Ревью плана проверки: требуется» → независимый ревьюер ДО implementer'а; п. 4 даёт этому ревьюеру на вход «дифф от merge-base» — до кода диффа нет | Оркестратор не может выполнить оба пункта буквально | Разнести: до кода — ревью QA_PLAN по TASK + реестру; после кода — TEST_PLAN_REVIEW по диффу (здесь сделано второе) |
| K-12 | `git.base_branch` / агенты | Ветка задачи стоит на `chore/agent-kit`, а `base_branch: main` → `merge-base` захватывает коммиты установки kit; исполнитель сам заметил и предложил базу `317f74c` | Ревьюер по контракту смотрит дифф от merge-base — получил бы 5 тыс. строк kit | Поддержать «базу задачи» в STATE/флаге промта (`BASE: <ref>`), который читают reviewer/qa-report/deliver |
| K-13 | `kit-acceptance` (frontmatter `tools: … ToolSearch`) | Агент сообщил, что ToolSearch в его сессии не было → браузерные MCP не загрузить; взял Playwright из кэша npx, Firefox не запустился (песочница), WebKit не скачан | Приёмка UI зависит от случайного кэша на машине | В `kit-acceptance` — явный порядок: MCP-браузер → `npx playwright` с установкой браузера (по «да») → BLOCKED; в `qa.surface` — проверка доступности на шаге 0 |
| K-14 | Конвейер в целом | Автор (60 тестов), ревьюер (2 прохода, APPROVED) и QA-отчёт (62 PASS) не заметили, что «сегодня» в UI-тестах = реальная дата; поймал только независимый ревьюер плана тестов мутацией `now() → new Date()` | Довод в пользу обязательности TEST_PLAN_REVIEW при риске ≥ medium — он окупился | Оставить; в чек-лист kit-reviewer добавить «закреплённое время не совпадает с реальным днём прогона» |
| K-15 | Сверка находок главной сессией (`rules/adversarial-review.md`) | Моя диспозиция TF-8 «тест на внешнюю смену `value` (или удалить код, если недостижим)» → исполнитель удалил код, недостижимость не доказал → регресс F-7 на проходе 3, когда лимит проходов уже исчерпан | Диспозиция с «или» перекладывает решение на исполнителя без проверки условия | В правило сверки: диспозиция — одно действие; «удалить, если недостижим» — только с доказательством недостижимости (тест/grep) в CHANGES.md |
| K-16 | `pipeline.max_review_passes` | Лимит считает проходы по артефакту, но после прохода 2 добавился большой круг (баги приёмки + ревью плана тестов, 11 коммитов) — на него остался один проход | Новый объём кода получает меньше ревью, чем первый | Считать проходы на каждый круг исправлений (или сбрасывать счётчик после FAIL приёмки) |
| K-17 | `check_gates.py` (QA_PLAN_FOR sha) vs диспозиция UPDATE-DOC | Ревьюер требует поправить PLAN.md (UPDATE-DOC → `NEEDS_CHANGES`), но любая правка PLAN.md ломает sha-привязку QA_PLAN и требует перезапустить kit-qa-planner — ради одной фразы | Нет дешёвого пути закрыть UPDATE-DOC по плану; главная сессия вынуждена отступать от контракта | Ввести `PLAN_ERRATA.md` (не входит в sha) как место для UPDATE-DOC по плану после реализации, и учитывать его в вердикте ревью |
